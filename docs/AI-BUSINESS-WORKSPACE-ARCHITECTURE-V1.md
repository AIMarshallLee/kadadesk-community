# KADAdesk AI 经营工作台｜架构基线 V1（2026-10-28）

> 状态：阶段性落地，不是生产就绪声明。本次 PR 将最小可信跨插件任务连接到本地工作台。其余阶段属于后续实施规划。

## 产品边界

咔哒是可插拔的 AI 经营工作台，服务「内容获客 → 客户线索 → 销售跟进 → 订单/服务 → 复购」等业务流程。商家看到的是任务和业务成果，不需要面对 Agent 的命令行。

- 公共仓库 kadadesk-community：可信基础工作台、公开插件契约、可授权重用的非敏感模块和贡献者协作。
- 私有仓库 kadadesk：原始历史、商业交付、商户/租户权限、计费、获批渠道连接器和可能受限的第三方组件。
- 暂不新建第三个产品主仓；跨仓共享 Core 的版本化复用尚需实施，不能宣称已经自动同步或复用。
- 不将个人账号外挂、未经授权的消息批量发送、绕过平台规则的功能纳入产品路线。

## 分层目标

    用户：任务入口 / 审核工作台 / 操作记录 / 行业模板
                   |
    业务编排层：trusted workflows / 状态 / 人工确认 / 失败阻断
                   |
    插件宿主：版本 / 最小权限 / 可撤销启停 / 数据边界
           |                 |                 |
       内容与素材         已审核知识          企业授权连接器
           |                 |                 |
    执行适配层：官方 API 优先；受控浏览器或本地执行仅在获准时启用
                   |
    数据层：本地单用户（现状）→ 组织 / 租户 / 审计（尚未实现）

Core 不依赖具体社交平台；AI 模型、内容生产、SEO/GEO、网站建设、CRM、企微与订单系统由可替换插件/连接器提供。禁止把第三方库的“GitHub 可见”当作商业许可。

## 本阶段代码已经接入的最小链路

1. 已有 plugin-host.ts：两个可信内置模块，启停状态持久化；停用后业务路由拒绝。
2. 新增 sdk/workflow-contracts.ts：可供后续模块依赖的任务状态与结果字段（V1）。
3. 新增 server/task-runner.ts：仅允许源码内注册的任务。通过本地鉴权路由 GET /api/tasks 查看，POST /api/tasks/knowledge-to-content 执行。
4. 首个受控任务：已审核知识库检索 → 提炼资料到内容运营草稿。只能检索已审核且启用的知识，不接模型、不自动外发、不创建账号发布任务。输出是需人工核对的资料整理草稿，不是可直接发布的营销文案。
5. 任务本地持久化并保留最近 100 条状态。关闭/重启时处于 running 的任务转为 interrupted，不自动重放（防止已有草稿时创建重复内容）。若处理或持久化异常，人工检查内容草稿与状态。
6. 浏览器 UI 新增「任务编排」入口和本机任务记录。与现有 localhost token、Origin/Host 限制共用安全边界。

**没有实现：** 可下载动态插件、第三方 JavaScript 沙箱、企业权限隔离、真正的任务队列、后台长期运行、跨设备云同步、智能视频制作、企微授权连接器、AI 自动营销、Mac/Windows 原生端任务系统。

## 后续 PR 必须逐项验收

| 里程碑 | 最小交付和证据 | 推荐任务归属 |
| --- | --- | --- |
| M1 插件 SDK | content-ops 拆出独立 manifest / 依赖 / 生命周期；插件停用后正在排队的任务不会继续写业务数据；故障隔离测试 | 社区 Core |
| M2 知识/素材能力 | 合法授权的文档导入、审核追溯、来源引用、合规素材预览；边界数据测试 | 社区插件 |
| M3 商业增长链路 | 内容、SEO/GEO、CRM、客户服务分别用独立插件，使用同一任务协议；用模拟客户全链路测试 | 可公开模块与私有企业组件分离 |
| M4 企业连接器 | 企微/网站/订单系统官方接口，按使用主体与 API 权限逐项验收，记录撤权与失败恢复 | 私有商业版，公开示例须有许可 |
| M5 企业产品化 | 租户隔离、RBAC、审计、计量、安装升级和回滚，Mac/Windows 真机验收 | 私有商业版 |

**需要明确的技术债：** 当前 plugin-host 为源码内置模块的开关，不是插件沙箱；任务 runner 也是单机受控示例，不等同于生产级编排引擎。未来任务队列、插件停用与在途任务写入之间必须采用统一权限闸门和一致性机制。

## 社区贡献规则

- 优先认领独立小模块、测试、文档和可信 API 适配。先 Issue 写明功能、依赖、授权、预期数据流与人工审核点，再做 PR。
- PR 必须提供成功路径与失败路径测试，并运行 node scripts/verify-publication.mjs、npm test、npm run smoke。
- 必须明确第三方依赖的许可证及商业分发/SaaS 限制；无需引入依赖就能做的，不新增依赖。
- 使用虚构样本；不得提交真实客户数据、凭证、账号会话、未获授权源码或原始私有仓库历史。
- 社区贡献不会自动授予项目所有者商业再授权权利。需要双许可的贡献，合并前另行确认书面授权。
- 提供可重复的本机操作验证与 GitHub Actions CI，不能把 CI 成功等同于实际平台生产验收。
